## 2. 核心业务功能

### 2.1 课程生产

课程生产端需要支持：

- 动作库管理；
- 动作类型管理；
- 单个/批量视频上传；
- 视频封面与服务端缩略图；
- 课程基础信息；
- 热身、正式训练、冷身；
- Pod 编排；
- 单屏瀑布流和多屏站点模式；
- 站点编号、训练目标、work/rest/switch 配置；
- 课程计划文字内容；
- 模板套用；
- 课程复制、删除、保存；
- 按课程包隔离内容。

难点在于课程脚本既要给编课者可视化编辑，又要能被 TV 精确播放。

### 2.2 现场控课

Coach 端承担门店现场工作流：

- 查看当前场馆当前课程包今日课表；
- 查看课程计划；
- 预览课程；
- 开始课程；
- 暂停、继续、终止、结束；
- 刷新 TV 课表；
- 绑定/解绑屏幕；
- 查看屏幕在线、状态、版本、缓存情况；
- 切换场馆已绑定课程包。

难点在于 Coach 操作必须通过 Server 校验场馆权限，并通过 MQTT 通知所有 TV，但 TV 仍以 Server session 为准。

### 2.3 TV 多屏播放

TV 端关键能力：

- 未绑定二维码；
- 场馆与屏幕号绑定；
- 心跳上报；
- 拉 daily-checksum；
- 拉 daily-bundle；
- 下载/校验课程资源；
- 根据屏幕号展示竖屏/横屏不同 UI；
- warm up / training / cool down 时序；
- Pod work/rest/move station/hydrate/move zone；
- 本地缓存优先播放；
- 断网、重连、重试；
- APK 静默/半自动更新；
- 接收并处理 preview/start/pause/resume/end/terminate。

难点是现场稳定性，多屏同步，弱硬件视频播放和资源缓存。

### 2.4 场馆与课程包

系统不是单一门店架构，而是从一开始考虑多场馆：

- 场馆有独立 namespace；
- 场馆绑定课程包；
- 场馆有当前启用课程包；
- Coach/TV 看到的课表来自当前启用课程包；
- 课程包可以复用给多个场馆；
- 编课账号可按课程包授权。

该模型是未来直营/加盟/托管复制的重要基础。

## 3. 未来需求点

此前已讨论的未来需求包括：

这些未来需求会把项目从“课程和 TV 控课系统”扩展成“团课健身房操作系统”。

## 4. 与普通系统的差异

普通外包后台通常是：

- 表单；
- 列表；
- CRUD；
- 权限；
- 简单报表。

Infini 的差异在于：

- 需要结构化课程脚本；
- 需要 Android TV 本地播放；
- 需要多屏同步；
- 需要实时控制与权威状态结合；
- 需要媒体缓存和版本更新；
- 需要门店现场可用，不能只在测试环境可用；
- 需要未来复制到多门店。
